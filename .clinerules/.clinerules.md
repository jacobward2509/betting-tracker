# Cline Project Rules

This file is intentionally short. Each workflow's full detail lives in `playwright/docs/workflows/`. Read the **Workflow State** section below before starting _any_ task — it applies across every workflow in this repo.

---

## Workflow State

Before beginning any task:

1. Read `.ai/workflow-state.json`.
2. Determine the current workflow stage.
3. Never repeat a completed stage.
4. After completing a stage, immediately update `workflow-state.json`.
5. If the state file and the conversation disagree, trust the state file.

If `.ai/workflow-state.json` doesn't exist yet, there is no active workflow — proceed normally and create it at the first checkpoint (see each workflow file's "Workflow State Checkpoint" section).

| Field                       | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workflow`                  | Always `"api-test-generation"` for this repo's flows.                                                                                                                                                                                                                                                                                                                                                                                                             |
| `apiVersion`                | `"V1"` or `"V2"` — determines which stages are relevant (see below).                                                                                                                                                                                                                                                                                                                                                                                              |
| `ticket`                    | Jira ticket key, once known/confirmed. `null` until then.                                                                                                                                                                                                                                                                                                                                                                                                         |
| `endpoint`                  | Method/path/operationId for the endpoint being worked.                                                                                                                                                                                                                                                                                                                                                                                                            |
| `testPlanFile` / `specFile` | Paths to the generated artifacts, once they exist.                                                                                                                                                                                                                                                                                                                                                                                                                |
| `stage`                     | The current stage — see below.                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `completed`                 | Ordered list of stages fully finished.                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `task`                      | Free-text description of what's actively being worked (e.g. the specific failure being repaired, or which phase of repair triage things are in).                                                                                                                                                                                                                                                                                                                  |
| `failures`                  | Only present once `stage` reaches `"repair"`. One entry per failure from the run's failure report. `decision` is `null` until the user chooses, then one of `"self-heal"` / `"raise-bug"` / `"skip"`. `status` is `"undecided"` → (`"fix-applied"` for self-heal / `"pending"` for raise-bug) → `"resolved"` once confirmed (fix passes re-run, bug ticket raised, or skip recorded). `"skip"` goes straight to `"resolved"` since there's nothing further to do. |
| `remainingRepairs`          | **Derived, not authoritative** — `failures.filter(f => f.status !== "resolved").length`. Recompute it every time `failures` changes; never edit it independently of `failures`, or the two will drift and the stage will stall.                                                                                                                                                                                                                                   |
| `stateAttachedToJira`       | Whether the completed state file has already been attached to Jira (or the user explicitly declined). Absent or `false` until resolved by `attach-workflow-state-to-jira.md`, which triggers automatically once `stage` reaches `"done"` with `remainingRepairs: 0`. Once `true`, do not re-offer attachment for this same completed state. If attached, the ticket key used is also recorded as `stateAttachedToJiraTicket`.                                     |

There is a second, lighter-weight `workflow` value for running **existing** spec coverage without going through `plan`/`jira`/`generate` — see **"api-test-execution" workflow** below for its schema differences.

### Stages (for `workflow: "api-test-generation"`)

| Stage      | Meaning                                                         | V1                    | V2                                                 |
| ---------- | --------------------------------------------------------------- | --------------------- | -------------------------------------------------- |
| `plan`     | Test plan being drafted                                         | ✅                    | ✅                                                 |
| `jira`     | Attach-to-Jira decision pending/resolved                        | ✅                    | ✅                                                 |
| `generate` | Postman collection (V1) / Playwright tests (V2) being generated | ✅                    | ✅                                                 |
| `run`      | Tests being executed and summarized                             | —                     | ✅                                                 |
| `repair`   | Working through failures (self-heal / raise bug / skip)         | —                     | ✅                                                 |
| `done`     | Workflow complete                                               | ✅ (after `generate`) | ✅ (after `repair`, or after `run` if no failures) |

V1 (Postman) workflows terminate at `done` right after `generate` — there's no automated run/repair loop for Postman collections in this repo.

⚠️ **V2 rule — never skip `run`:** When `apiVersion` is `"V2"`, completing `generate` must always advance `stage` to `"run"`. Setting `stage: "done"` immediately after `generate` is only valid for `"V1"`. Always check `apiVersion` in the state file before writing the next stage.

### "api-test-execution" workflow (running an existing spec file)

For running an **already-generated** V2 spec file (full file or specific describe block(s)) straight into run → repair, without `plan`/`jira`/`generate`, the state file uses `workflow: "api-test-execution"` instead, with these schema differences:

```json
{
  "workflow": "api-test-execution",
  "apiVersion": "V2",
  "specFile": "playwright/tests/api/quote-endpoints-v2.spec.ts",
  "scope": "full-file",
  "stage": "run",
  "completed": [],
  "task": "Running existing spec file ahead of repair triage",
  "remainingRepairs": 0,
  "stateAttachedToJira": false,
  "failures": []
}
```

- `scope` replaces `endpoint` for this workflow — either the literal `"full-file"`, or the describe name(s)/breadcrumb(s) selected (a string or array of strings).
- `ticket`, `endpoint`, and `testPlanFile` are omitted — there is no single new endpoint/ticket driving the run. A linked ticket, if needed later to raise a bug during repair, is instead derived from the current git branch at that point (see `self-heal.md`).
- Only these stages apply: `run → repair → done` — never `plan`, `jira`, or `generate`.
- `failures`, `remainingRepairs`, and the whole repair mechanism (self-heal / raise-bug / skip, Phase 1/Phase 2, resuming from state) work identically to the `api-test-generation` workflow — see `run-existing-spec.md` and `self-heal.md`.

### Starting a new workflow instance

If the user triggers a workflow for a **different** ticket/endpoint (`api-test-generation`) or a different `specFile`/`scope` (`api-test-execution`) than the one currently tracked in `.ai/workflow-state.json`, and that prior workflow isn't at `stage: "done"` (or is `"done"` with unresolved `remainingRepairs`), tell the user there's an incomplete workflow in progress and confirm whether to abandon/overwrite it or finish it first before starting a new one.

If the user chooses to **abandon and overwrite**, before the existing state file is overwritten, offer to attach its current (partial) contents to a Jira ticket — see `playwright/docs/workflows/attach-incomplete-state-to-jira.md`, which triggers automatically at that point. Only once that workflow resolves (attached, failed, or declined) should the new workflow's initial state be written.

### Resuming

If `.ai/workflow-state.json` says `stage: "repair"`, don't re-ask which failures to work on or re-collect decisions already recorded — read the `failures` array and resume exactly where it left off (see `self-heal.md`'s "Resuming from state" section):

- Any entry with `decision: null` (`status: "undecided"`) still needs a decision from the user.
- Any entry with `status: "fix-applied"` already has a code fix in place, pending Phase 2 re-run confirmation — don't re-investigate or re-propose a fix.
- Any entry with `status: "pending"` (decision `"raise-bug"`) is waiting on Phase 2 to raise the ticket — don't re-ask which failures should get bugs.
- Any entry with `status: "resolved"` is done — never revisit it.

## Workflows

None of the files below are auto-loaded — only this file (`clinerules.md`) and the Workflow State rules above are. When a trigger phrase matches (or a workflow's own instructions say to move to the next one), **read the corresponding file in full before doing anything else**; don't rely on having seen it earlier in the conversation, and don't act on a stage's rules from memory.

| Trigger phrase                                                                                                              | Read this file                                                 |
| --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |

`playwright/docs/api-test-scenarios.md` and `playwright/docs/playwright-api-test-generation.md` follow the same on-demand pattern — each workflow file above says exactly when to read them.

The overall flow for a V2 endpoint is:

```
plan → jira → generate → run → repair → done
```

For a V1 endpoint:

```
plan → jira → generate → done
```

For running an existing spec file/describe block (`api-test-execution` workflow):

```
run → repair → done
```

Each linked file documents exactly when and how to update `.ai/workflow-state.json` at its own checkpoints — follow those instructions as you go rather than waiting until the end of a task.
