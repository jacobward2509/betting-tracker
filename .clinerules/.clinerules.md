# Cline Project Rules

This file is intentionally short. Each workflow's full detail lives in `playwright/docs/workflows/`. Read the **Workflow State** section below before starting _any_ task — it applies across every workflow in this repo.

---

## Workflow State

There are two independent, parallel workflow families in this repo — **API** test generation and **UI** test generation — each tracked in its own state file. They never block or conflict-check against each other; only workflows of the *same* family conflict-check.

| Family | State file | Workflow value(s) |
| --- | --- | --- |
| API | `.ai/api-workflow-state.json` | `api-test-generation`, `api-test-execution` |
| UI | `.ai/ui-workflow-state.json` | `ui-test-generation` |

Before beginning any task:

1. Determine which family the task belongs to (trigger phrase, or explicit mention of "API"/"UI" test plan/tests). If genuinely ambiguous, ask the user.
2. Read that family's state file (`.ai/api-workflow-state.json` or `.ai/ui-workflow-state.json`).
3. Determine the current workflow stage.
4. Never repeat a completed stage.
5. After completing a stage, immediately update the relevant state file.
6. If the state file and the conversation disagree, trust the state file.

If the relevant state file doesn't exist yet, there is no active workflow for that family — proceed normally and create it at the first checkpoint (see each workflow file's "Workflow State Checkpoint" section).

There is a second, lighter-weight `workflow` value for running **existing** spec coverage without going through `plan`/`jira`/`generate` — see **"api-test-execution" workflow** below for its schema differences.

### Stages (for `workflow: "api-test-generation"`)

| Stage      | Meaning                                                         | V1                    | V2                                                 |
| ---------- | --------------------------------------------------------------- | --------------------- | -------------------------------------------------- |
| `plan`     | Test plan being drafted                                         | ✅                    | ✅                                                 |
| `jira`     | Attach-to-Jira decision pending/resolved                        | ✅                    | ✅                                                 |
| `generate` | Postman collection (V1) / Playwright tests (V2) being generated | ✅                    | ✅                                                 |
| `run`      | Tests being executed and summarized                             | —                     | ✅                                                 |
| `repair`   | Working through failures (self-heal / raise bug / skip)         | —                     | ✅                                                 |
| `done`     | Workflow complete                                               | ✅ (after `generate`) | ✅ (after `repair`, or after `run` if no failures) |

V1 (Postman) workflows terminate at `done` right after `generate` — there's no automated run/repair loop for Postman collections in this repo.

⚠️ **V2 rule — never skip `run`:** When `apiVersion` is `"V2"`, completing `generate` must always advance `stage` to `"run"`. Setting `stage: "done"` immediately after `generate` is only valid for `"V1"`. Always check `apiVersion` in the state file before writing the next stage.

### "api-test-execution" workflow (running an existing spec file)

For running an **already-generated** V2 spec file (full file or specific describe block(s)) straight into run → repair, without `plan`/`jira`/`generate`, the state file uses `workflow: "api-test-execution"` instead, with these schema differences:
```json
{
  "workflow": "api-test-execution",
  "apiVersion": "V2",
  "specFile": "playwright/tests/api/quote-endpoints-v2.spec.ts",
  "scope": "full-file",
  "stage": "run",
  "completed": [],
  "task": "Running existing spec file ahead of repair triage",
  "remainingRepairs": 0,
  "stateAttachedToJira": false,
  "failures": []
}
```

- `scope` replaces `endpoint` for this workflow — either the literal `"full-file"`, or the describe name(s)/breadcrumb(s) selected (a string or array of strings).
- `ticket`, `endpoint`, and `testPlanFile` are omitted — there is no single new endpoint/ticket driving the run. A linked ticket, if needed later to raise a bug during repair, is instead derived from the current git branch at that point (see `self-heal.md`).
- Only these stages apply: `run → repair → done` — never `plan`, `jira`, or `generate`.
- `failures`, `remainingRepairs`, and the whole repair mechanism (self-heal / raise-bug / skip, Phase 1/Phase 2, resuming from state) work identically to the `api-test-generation` workflow — see `run-existing-spec.md` and `self-heal.md`.

### Starting a new workflow instance

If the user triggers a workflow for a **different** ticket/endpoint (`api-test-generation`) or a different `specFile`/`scope` (`api-test-execution`) than the one currently tracked in `.ai/api-workflow-state.json`, and that prior workflow isn't at `stage: "done"` (or is `"done"` with unresolved `remainingRepairs`), tell the user there's an incomplete API workflow in progress and confirm whether to abandon/overwrite it or finish it first before starting a new one. The same rule applies independently for `ui-test-generation` against `.ai/ui-workflow-state.json` — a different scope than the one currently tracked there triggers the same abandon/finish check, scoped to the UI state file only. **The two families never conflict-check against each other** — starting a UI workflow never requires resolving an incomplete API workflow, and vice versa.

If the user chooses to **abandon and overwrite**, before the existing state file is overwritten, offer to attach its current (partial) contents to a Jira ticket — see `playwright/docs/workflows/attach-incomplete-state-to-jira.md` (API) or `playwright/docs/workflows/attach-incomplete-ui-state-to-jira.md` (UI), whichever triggers automatically at that point. Only once that workflow resolves (attached, failed, or declined) should the new workflow's initial state be written.

### Resuming

If the relevant state file says `stage: "repair"`, don't re-ask which failures to work on or re-collect decisions already recorded — read the `failures` array and resume exactly where it left off (see `self-heal.md`'s "Resuming from state" section for API, or `ui-self-heal.md`'s equivalent section for UI):

- Any entry with `decision: null` (`status: "undecided"`) still needs a decision from the user.
- Any entry with `status: "fix-applied"` already has a code fix in place, pending Phase 2 re-run confirmation — don't re-investigate or re-propose a fix.
- Any entry with `status: "pending"` (decision `"raise-bug"`) is waiting on Phase 2 to raise the ticket — don't re-ask which failures should get bugs.
- Any entry with `status: "resolved"` is done — never revisit it.

## UI Workflow (`ui-test-generation`)

Mirrors the API workflow's stage sequence and repair mechanics, but with **no V1/V2 split** — there's only ever one flavor of UI test generation — and `specFiles` is plural, since one UI test plan's scenarios can span multiple tier files (`smoke/`, `functional/`, `e2e/`) in a single generation pass.

### UI Schema

```json
{
  "workflow": "ui-test-generation",
  "ticket": "UI-42",
  "scope": {
    "page": "AuthView",
    "route": "/auth",
    "description": "Login + signup form"
  },
  "testPlanFile": "playwright/docs/test-plans/ui/auth/ui-test-plan-auth.md",
  "specFiles": [
    "playwright/tests/smoke/auth-page.spec.ts",
    "playwright/tests/functional/auth-signup-preferences.spec.ts"
  ],
  "stage": "run",
  "completed": ["plan", "jira", "generate"],
  "task": "Generated smoke + functional coverage for the auth page; awaiting run confirmation.",
  "remainingRepairs": 0,
  "stateAttachedToJira": false,
  "failures": []
}
```

| Field | Meaning |
| --- | --- |
| `workflow` | Always `"ui-test-generation"`. |
| `ticket` | Jira ticket key, once known/confirmed. `null` until then. |
| `scope` | The page/component/journey being covered — `page` (component name), `route` (URL pattern), `description` (free text clarifying single-page vs. page-group scope). |
| `testPlanFile` | Path to the generated UI test plan markdown file, once it exists. |
| `specFiles` | **Plural** — array of spec file paths written during `generate`, spanning whichever of `smoke/`, `functional/`, `e2e/` the plan's scenarios required. Empty array until `generate` completes. |
| `stage` | Same stage sequence as API: `plan → jira → generate → run → repair → done`. No V1/V2 fork — there is no "generate always advances to run" caveat to check, since UI has only one flavor and it always has a run/repair loop. |
| `completed` | Ordered list of stages fully finished. |
| `task` | Free-text description of what's actively being worked. |
| `remainingRepairs` / `failures` | Identical semantics and mechanics to the API schema — see the API Schema field table above. |
| `stateAttachedToJira` / `stateAttachedToJiraTicket` | Identical semantics to the API schema. |

### Stages (`ui-test-generation`)

| Stage | Meaning |
| --- | --- |
| `plan` | UI test plan being drafted |
| `jira` | Attach-to-Jira decision pending/resolved |
| `generate` | Playwright UI tests being generated into one or more tier spec files |
| `run` | Tests being executed and summarized |
| `repair` | Working through failures (self-heal / raise bug / skip) |
| `done` | Workflow complete |

There is no V1/V2-style fork — `generate` always advances to `run` (UI always has a run/repair loop, unlike V1/Postman on the API side).

### Stage Sequences

The overall flow for a V2 API endpoint is:

```
plan → jira → generate → run → repair → done
```

For a V1 API endpoint:

```
plan → jira → generate → done
```

For running an existing API spec file/describe block (`api-test-execution` workflow):

```
run → repair → done
```

For a UI test plan (`ui-test-generation` workflow — no V1/V2 split):

```
plan → jira → generate → run → repair → done
```

Each linked file documents exactly when and how to update its family's state file (`.ai/api-workflow-state.json` or `.ai/ui-workflow-state.json`) at its own checkpoints — follow those instructions as you go rather than waiting until the end of a task.
